# Разделы 3.2-3.5 для курсовой работы

## 3.2 Установка и настройка

Установка и настройка программной системы Tournament Maker начинается с получения исходного кода проекта из репозитория. После клонирования необходимо перейти в директорию проекта и подготовить серверную часть приложения. Backend реализован на Python с использованием FastAPI, поэтому перед запуском создается виртуальное окружение, активируется оно и устанавливаются зависимости проекта.

Для хранения данных используется PostgreSQL. В проекте предусмотрен запуск базы данных через Docker Compose, поэтому пользователю не требуется вручную создавать базу и настраивать сервер PostgreSQL. После запуска контейнера базы данных необходимо создать файл переменных окружения `.env` на основе `.env.example`. В нем указываются параметры подключения к базе данных, секретный ключ JWT, режим работы приложения и разрешенные адреса клиентской части.

После настройки окружения выполняются миграции Alembic, которые создают таблицы пользователей, сезонов, команд, игроков, стадионов, судей, турниров, матчей, составов, протоколов, турнирной таблицы и статистики. Затем backend запускается через Uvicorn и становится доступен по адресу `http://127.0.0.1:8000`. Проверить работу сервера можно через endpoint `/health`, а документацию API - через Swagger UI по адресу `http://127.0.0.1:8000/docs`.

При необходимости можно запустить клиентскую часть приложения. Она реализована на React и используется для взаимодействия пользователя с backend API. Также проект можно запустить целиком через Docker Compose, что удобно для демонстрации работы системы.

Более подробная инструкция по установке и настройке проекта приведена в репозитории проекта [16] в папке `docs`, а основные команды приведены в приложении В.

## 3.3 Тестирование

Тестирование Tournament Maker выполнялось для проверки корректности работы backend-приложения, API и основных бизнес-правил системы. Основное внимание уделялось авторизации, изоляции данных пользователей, работе с командами, игроками, стадионами, сезонами, турнирами, матчами, расписанием, протоколами, турнирной таблицей и статистикой игроков.

Для автоматического тестирования используется `pytest`. Тесты расположены в папке `backend/tests`. В них проверяется регистрация и вход пользователя, получение JWT-токена, выполнение CRUD-операций, генерация расписания чемпионата, работа кубкового турнира, создание составов, заполнение протоколов матчей, генерация случайных результатов, пересчет турнирной таблицы и статистики игроков.

Дополнительно выполняется проверка качества кода с помощью `ruff` и `black`. Это позволяет поддерживать единый стиль кода и находить часть ошибок до запуска приложения. Также проверяется корректность миграций Alembic, чтобы структура базы данных соответствовала ORM-моделям.

Ручное тестирование выполнялось через Swagger UI и пользовательский интерфейс. Проверялось, что пользователь может войти в систему, получить доступ к своим данным, создать турнир, сформировать расписание, внести результат матча и посмотреть обновленную статистику. Отдельно проверялась защита данных: один пользователь не должен видеть или изменять данные другого пользователя.

Более подробное описание тестовых сценариев и команд проверки приведено в репозитории проекта [16] в папке `docs`.

## 3.4 Ввод в эксплуатацию

Ввод приложения в эксплуатацию включает подготовку окружения, запуск базы данных, настройку переменных окружения, применение миграций, запуск backend-сервера и проверку его работоспособности. В рамках курсовой работы эксплуатация рассматривается как локальный или демонстрационный запуск проекта.

После запуска backend пользователь может работать с системой через API или через клиентскую часть. Основной сценарий эксплуатации включает регистрацию или вход пользователя, создание сезона, добавление команд, игроков и стадионов, создание турнира, формирование расписания, заполнение протоколов матчей и просмотр турнирной таблицы со статистикой.

Для демонстрации предусмотрен скрипт наполнения данными. Он создает demo-пользователя и добавляет начальные сведения о сезоне, турнирах, командах, стадионах, игроках, судьях и матчах. Это позволяет быстро проверить работу системы без ручного ввода большого количества данных.

В процессе эксплуатации система проверяет входные данные, защищает маршруты с помощью JWT-токена и разделяет данные разных организаторов через поле `owner_id`. Также backend контролирует предметные ограничения: команда не может играть несколько матчей в один день, судья не может быть назначен на параллельные матчи, а завершенные матчи нельзя изменять обычными операциями редактирования.

Более подробная инструкция по вводу проекта в эксплуатацию приведена в репозитории проекта [16] в папке `docs`.

## 3.5 Разработка сопроводительной документации

В ходе разработки Tournament Maker была подготовлена сопроводительная документация, необходимая для установки, запуска, тестирования и дальнейшего сопровождения проекта. Документация хранится в репозитории вместе с исходным кодом, поэтому ее можно обновлять одновременно с изменением приложения.

Основным документом для запуска backend-части является `backend/README.md`. В нем описаны требования к окружению, порядок установки зависимостей, запуск PostgreSQL, настройка `.env`, применение миграций, запуск сервера, проверка healthcheck и выполнение тестов.

Для описания архитектуры и предметной области используются файлы в папке `docs`. В них отражены основные сущности системы, бизнес-ограничения, структура backend-приложения, правила работы с расписанием, кубковым турниром, матчами, составами, протоколами, турнирной таблицей и статистикой.

Отдельным видом документации является автоматически формируемая OpenAPI-документация. После запуска backend она доступна через Swagger UI и ReDoc. С ее помощью можно посмотреть список endpoint-ов, структуру запросов и ответов, а также выполнить тестовые запросы к API.

Более подробная сопроводительная документация приведена в репозитории проекта [16] в папке `docs`.

# Приложение В. Последовательность команд

Примечание: команды `uvicorn`, `npm run dev` и `docker compose up --build` запускают долгоживущие процессы, поэтому обычно выполняются в отдельном терминале.

## Листинг В.1 - клонирование репозитория

```powershell
git clone https://github.com/gvritia/gvriti-Tournament-Maker.git
cd gvriti-Tournament-Maker
```

## Листинг В.2 - установка зависимостей backend

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

## Листинг В.3 - создание файла переменных окружения

```powershell
Copy-Item .env.example .env
```

## Листинг В.4 - запуск базы данных

```powershell
cd ..
docker compose up -d db
```

## Листинг В.5 - применение миграций

```powershell
cd backend
alembic upgrade head
```

## Листинг В.6 - запуск backend

```powershell
uvicorn app.main:app --reload
```

## Листинг В.7 - проверка backend

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
```

## Листинг В.8 - наполнение demo-данными

```powershell
python -m app.scripts.seed_demo_data `
  --clubs-csv "C:\Users\user\PycharmProjects\parsing_footbal_clubs\laliga_clubs.csv" `
  --squads-csv "C:\Users\user\PycharmProjects\parsing_footbal_clubs\laliga_squads.csv"
```

## Листинг В.9 - запуск frontend

```powershell
cd ..\frontend
npm install
npm run dev
```

## Листинг В.10 - запуск всего проекта через Docker Compose

```powershell
cd ..
docker compose up --build
```

## Листинг В.11 - запуск тестов и проверок

```powershell
cd backend
pytest
ruff check .
black --check .
alembic check
```
